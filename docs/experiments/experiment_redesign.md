# 实验优化方案：先解决缺失字段编造，再扩大评测

审阅日期：2026-11-17。500 条最终设计。已生成离线样本清单并复核历史结果；未启动新模型推理，以下新实验效果均待验证。

## 1. 当前证据与需要纠正的结论

- `eval_extraction_results.json` 当前保存的是 temperature=0.5、5000 条、全字段全对率 100%；文档记录的 temperature=0.1 结果没有在这个文件中独立保留。脚本固定输出路径会覆盖旧结果，不能把现有文件当作两个条件的原始证据。
- `eval_missing_results.json` 保存的是 temperature=0.1、500 条：可解析率和在场字段正确率均为 100%，1000 个缺失字段中 792 个被填值，旧脚本称其为“编造率”79.2%（更准确的名称是缺失字段非 null 填值率）；旧规则下整条通过率仅 15.8%。这比继续测试简单抄写任务更有研究价值。
- 缺失变体提示仍要求全部字段及其非空类型，没有明确“缺失输出 null”。当前结果测量的是这种提示下的行为，不能直接归因于模型无法遵循缺失处理规则。
- 两个评测脚本都是串行调用，但没有显式生成上限、批间休息和逐条持久化。串行不等于低持续负载。结果文件时间不足以证明黑屏时是哪一个进程在推理。
- 系统日志在 11:32–11:34 出现过热紧急休眠；本方案不采用防睡眠方式绕过热保护。

## 2. 优先实验：缺失处理协议是否有效

问题：明确缺失处理规则，是否降低编造，同时保持已提供字段的抽取准确率？

从基础数据按申请人 ID 固定抽取 **500 人**，排除已用于缺失错误分析的旧 500 人。每人只生成一条本轮案例，开发集与测试集无 ID 重叠。原始 5000 条都接受过完整档案基线测试，因此新测试集仅是本次缺失处理优化的留出集，并非从未评估过的外部数据。

| 分区 | 完整档案 | 删除两字段 | 总样本 | A/B 各一次的调用数 |
|---|---:|---:|---:|---:|
| 开发集 | 0 | 100 | 100 | 200 |
| 锁定测试集 | 100 | 300 | 400 | 800 |
| 合计 | 100 | 400 | 500 | 1000 |

缺失字段均衡：开发集每个字段被删除 20 次；测试集每个字段被删除 60 次。完整档案用来检测新增规则是否导致本来有值的字段被误判为 null。第一轮只研究缺失处理；冲突、干扰文本和 schema 强约束留到下一轮，避免一次改变过多因素。

| 条件 | 变化 | 目的 |
|---|---|---|
| A 原提示 | 保留原有字段和类型要求 | 测原基线 |
| B 明确缺失规则 | 仅补充：全部字段保留且允许 null，未提供必须为 null，不推测、不补算，不用 0/空字符串/“未知”占位，明确提供的 0 仍为 0 | 测缺失协议的作用 |

先取开发集 10 人校准输出上限和运行时间，再完成开发阶段。开发集可以调提示，但每次修改独立留档，额外调用另计。完成后冻结 B 的提示和全部参数，再执行 400 人配对测试；不能边看测试结果边改提示。每个样本条件顺序交替平衡、样本顺序固定随机化。1000 次是各条件只跑一遍的预算，校准重跑和调试会增加调用。

固定模型版本、量化、上下文、temperature=0.1、采样参数和 seed；A/B 在同一样本上配对，按小块随机、平衡顺序，避免总是把 B 放到机器更热的后半段。主测试每样本每条件一次；若后续研究随机性，另设多个 seed 的实验，不与主比较混合。

首轮不扫 top_p/top_k，也不再跑一轮 5000 条完整档案。冲突文本、单位转换、干扰段落作为下一轮独立任务；先规定冲突时的正确处理方式，再生成真值。

## 3. 评分必须区分格式、内容和运行失败

1. 严格 JSON 对象率：整个回答必须直接解析为对象；代码围栏和额外文字不合格。另报宽松恢复率，保留现有提取 JSON 的能力但不混为严格成功。
2. Schema 合规率：检查字段、额外字段、类型、null；拒绝用布尔值或数字字符串冒充数值。
3. 已提供字段准确率：主指标分母包含全部计划样本的在场字段；解析失败计为失败。另报解析成功条件下的准确率。
4. 缺失字段非空填值率：分母和解析失败处理必须显式说明。条件编造率只在可解析对象中计算；同时报告全样本的“缺失字段正确输出 null 率”和解析/请求失败率，不能将不可解析回答当作没有编造。
5. 整条成功率：格式合规、在场字段正确、全部缺失字段为 null，三者同时成立。
6. 数值抽取按输入展示精度比对；现有 0.1% 相对容差会放过金额抄写错误，改为十进制定点精度比较。单位换算另设容差协议。

报告 A/B 配对的改善和退化样本数、成功率差、按申请人重采样的置信区间；一个人的多个字段不视作独立样本。300 人缺失测试与 100 人完整对照用于方向判断和发现常见问题，不据此宣称极低错误率或生产级可靠性。调过提示的测试集转为开发集，下一次正式验证换新留出集。

## 4. 笔记本上的运行预算与恢复

下列数值是保守起点，不是已经验证过的散热安全阈值：

- 单实验进程、并发 1；启动前确认没有另一个本地模型任务同时跑。
- 先跑 10 条校准输出长度和延迟。短 JSON 暂用 4096 上下文、256 输出 token 上限；如果发生截断，检查输出内容及终止原因，再统一调整至 512，并将不同配置分开记录。不能直接套用旧报告“256 足够”。
- 每 20 条或累计推理 2 分钟（先到者）结束一个块，休息至少 60 秒；每轮最多 100 条或 15 分钟墙钟时间，到限保存退出，后续显式续跑。
- 休息时间不计入单请求延迟，但计入端到端实验完成时间。记录冷启动、预热与正式请求，分开统计。
- 温度/热压力若可可靠读取，出现系统热警告即停止发新请求。此前 `pmset -g therm` 读取失败，不能把它当作已具备的监控；没有可靠监控时不执行无人值守长跑。仅靠定时休息不能保证不会过热。
- 逐条追加 JSONL 并 flush，至少每块落盘；记录成功和失败。中断后按 run_id、样本 ID、条件、seed 去重续跑，校验数据与配置哈希，不复用不匹配的记录。
- 请求设置超时；错误不无限重试，原始失败与重试尝试分别保留。断网、服务异常、系统休眠均记录为运行事件。
- 独立运行目录保存配置、每条原始响应、耗时、token 数、终止原因、错误及汇总。禁止不同温度覆盖同一个结果文件。保留成功响应以支持评分器复核。

## 5. 原参数实验 A 的修订

- 原“吞吐”是输出 token 数 / (total_duration - load_duration)，包含提示处理时间，应标注为该口径下的有效吞吐；纯解码吞吐单独用 eval_count / eval_duration。
- 上下文每条件仅 1 次，且提示很短，只能说明该短输入的一次观测；不能宣称长文档吞吐不变。需要性能研究时，将上下文容量与实际输入长度分开，先选 4K/8K 两档，每档多次预热后测量，报告离散程度。
- `num_predict` 是生成上限，不保证实际输出等长；优先读取后端终止原因，并用输出完整性检查辅助，不能仅凭 token 数达到上限断言截断。
- 固定 seed 的 3 次相同只支持当前环境下的复现观察；固定模型 digest、后端版本与所有参数，不能承诺跨版本或跨硬件完全一致。
- 编辑距离衡量措辞变化，不等于事实正确、语义稳定或表达更自然。原报告相关判断应降为待验证假设。
- 现有报告“未观察到事实性失败”与其风险等级不一致案例存在张力；风险等级的正确性需要预先定义标签规则，不能拿某次自由回答充当真值。

## 6. 实施顺序

先修评分器、逐条保存与分批恢复；以人工构造的正常、null、缺字段、布尔值、非对象 JSON、额外文字、请求失败案例验证评分。随后进行开发集 10 人运行校准和 100 人开发比较，确定是否推进锁定测试。所有旧结果保留，只新增运行记录；本轮不直接启动全量实验。


## 7. 预先约定怎样下结论

以下是本项目用于筛选方案的候选目标，不是通用生产标准；应在测试前确认并固定：

- 主指标：300 人缺失测试的“整条成功率”。报告 B−A 的百分点差及按申请人配对重采样得到的 95% 区间；区间下界大于 0 才称为有改善证据。
- 实用性目标：B 的整条成功率至少 95%，缺失字段非 null 填值率不超过 1%；同时必须报告解析和请求失败，不能通过失败输出拉低填值率。
- 完整档案对照：100 人中 B 相比 A 不新增失败，作为回归筛查。即使零新增失败，也不宣称已经证明统计上的等效或生产安全。
- 既有数字、类别值不得因 null 规则丢失；对金额等字段的具体无依据填值单独列出，不能与空字符串、“未知”等占位值合并解释。
- 如果改善显著但达不到上述目标，结论是“提示规则有帮助，但仍需修正”。若无改善或出现完整档案退化，保留 A 的记录，回到开发集分析，不扩大到 5000 条。
- 延迟报告请求级中位数、P95，以及含休息的总墙钟时间。达到运行预算而退出时，报告已完成数量和失败数量，不将部分结果冒充完整测试。

## 8. 已有数据能支持的结论

完整档案当前存档：temperature=0.5，5000 条，按旧宽松解析器及数值容差评分全部通过。这支持“固定模板下直接抽取很容易”，不证明严格 JSON、金额逐位正确、复杂文本可靠或温度完全无影响；temperature=0.1 的原始结果被覆盖，不能完成严格双条件复核。

缺失档案当前存档：temperature=0.1，500 条。旧评分下 421 条至少有一个缺失字段填入非 null，79 条通过（15.8%）；1000 个缺失字段中 792 个填入非 null（79.2%）。对保存的 421 条失败响应离线复核得到：

| 缺失字段输出 | 次数 | 占全部 1000 个缺失字段 |
|---|---:|---:|
| 数字 0 | 343 | 34.3% |
| 空字符串 | 82 | 8.2% |
| 字符串“未知” | 101 | 10.1% |
| 其他非 null 值 | 266 | 26.6% |
| 旧规则通过：省略或 null | 208 | 20.8% |

最后一行由总数减去已保存失败事件推得，不能再拆分省略和 null，因为成功响应未保存。其他非 null 中包括缺失金额被填值、缺失贷款类型被填为“个人贷款”等。不能把 792 次全部表述为编造具体事实：其中 526 次是 0、空字符串或“未知”，但这些值仍可能给下游造成歧义，尤其 0 本身可能是有效业务值。

**现阶段结论：问题重点是缺失语义处理，而不是完整字段抄写能力；500 条足够用于这轮常见错误诊断和方案筛选。明确 null 的新提示值得验证，但是否有效、是否能达到目标，尚无新实测证据。**

系统热保护说明需要限制持续运行；减少到 500 条并不能单独保证散热安全。也没有证据证明温度参数 0.5 是机器过热原因，模型采样温度与硬件温度是不同概念。

- `data/processed/experiment_v3/dev.jsonl`：100 人开发清单，含 A/B 提示、真值、缺失字段及条件执行顺序。

- `data/processed/experiment_v3/manifest.json`：固定抽样种子、源数据与清单 SHA-256、调用预算及候选参数；状态为 `prepared_not_run`。

运行器仍需按第 3、4 节升级后才执行模型测试。原评测脚本不具备这些完整保护，不应直接全量启动。数据产物位于现有 gitignore 的目录，本机保留，源脚本用于复现。
